# ADR 0001: Інструмент IaC: AWS CloudFormation (YAML)

- Статус: Accepted
- Дата: 2026-11-05
- Milestone: M1 (діє для M2 до M5)

## Context

Вся робота йде в AWS Academy Learner Lab. Креденшали там тимчасові, сесія живе приблизно 4 години і при кожному старті лаби видається заново. Запис в IAM (`iam:CreateRole`, `iam:CreatePolicy` і подібне) скоріше за все заборонений, це я ще маю підтвердити розбором LabRole (див. `docs/m1-design-decisions.md`, розділ 7). На курсі ми проходили CloudFormation (лекція "2.1 IaC. CFN"), а контрольні питання M1 прямо питають про change sets і drift detection, тобто про можливості саме CloudFormation. Ще в M1 треба довести, що інфраструктуру можна знести і підняти з коду, і заміряти час. З M2 пайплайн CI/CD має розгортати інфраструктуру через IaC.

## Decision

Обираю AWS CloudFormation з шаблонами в YAML, причина проста: тут немає state файлу, який треба десь зберігати, бо стек сам і є станом і його тримає AWS. Це важливо в пісочниці, де креденшали міняються кожну сесію. Розгортаю через AWS CLI і завжди через явний change set (`create-change-set`, потім `describe-change-set`, потім `execute-change-set`), щоб перед кожною зміною бачити diff. Шаблони перевіряю офлайн через `cfn-lint` і онлайн через `aws cloudformation validate-template`.

## Alternatives rejected

| Альтернатива | Чому ні |
|---|---|
| Terraform (HCL) | Потрібен state файл. Локальний state живе на одному ноутбуці і легко губиться, а remote backend в S3 з lock таблицею це ще одна інфраструктура, яку треба підняти в пісочниці з креденшалами, що міняються щосесії. `plan` і `-refresh-only` по суті те саме, що change set і drift detection, але на захисті мені довелось би перекладати терміни. На курсі його не вчили. |
| AWS CDK | Він все одно генерує CloudFormation, тобто це ще один тулчейн (Node або Python) поверх того самого двигуна. `cdk bootstrap` за замовчуванням створює IAM ролі, а це в пісочниці майже напевно заборонено. Згенерований шаблон важче пояснити на захисті без нотаток. |
| Клікати в консолі і робити скріншоти | Це не відтворюється, тому завдання на recreatability і навичка INF-1 провалюються одразу. |
| Pulumi або OpenTofu | Та сама проблема зі state, що і в Terraform, і жодної переваги тут. |

## Consequences

Плюси такі. Перестворення це просто `delete-stack` і `create-stack`, без жодного state. Change set показує зміни до того, як вони застосовані, а drift detection показує ручні правки в консолі, і обидва я можу показати наживо на захисті. Стек працює з моїми власними креденшалами з пісочниці, тому окрема service role для CloudFormation не потрібна, а її я б і не зміг створити. Якщо в M2 буде Lambda, то AWS SAM це transform над CloudFormation, і рішення не ламається.

Мінус цього рішення в тому, що я прив'язуюсь до AWS, але весь курс на AWS, тому це терпимо. Ще YAML багатослівний і в ньому немає нормальних модулів, як у Terraform чи CDK, тому я тримаю мало шаблонів і роблю їх маленькими (ADR 0002). Exports між стеками створюють зв'язність, про це в ADR 0002. І є ризик, що операція зі стеком, запущена під кінець сесії, переживе креденшали, тому деплой і знесення я запускаю, коли на таймері лаби лишається хоча б 30 хвилин.

## Where it lives in code

- `infra/*.yaml` містить усі шаблони.
- `scripts/deploy-stack.sh` робить деплой через change set (показує diff і потім виконує).
- `scripts/drift-check.sh` запускає drift detection.
- `scripts/lint.sh` запускає `cfn-lint` і `validate-template`.
